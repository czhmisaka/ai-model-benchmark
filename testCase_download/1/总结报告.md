# AI 模型任务完成效率 · 总结册报告

> **测评周期**：2026-06-17  
> **参评模型**：5 款（deepseek-v4-pro / gpt-5.5 / Minimax-M3 / mimo-v2.5-pro / glm5.2 自费版）  
> **测评场景**：5 个（600k 海底捞针 / 数学能力 / 项目构建 / API 更新 / openClaw 工具）  
> **每场景轮次**：10 轮  
> **核心理念**：**任务完成效率 = 总耗时短 + 输出 Token 少**，单一指标（如 tokens/s）无法反映真实效率  
> **评价五维度**（严格区分「完成度」与「质量分」）：**① 效率（总耗时+Token）｜② 成功率（任务完成比例）｜③ 完成度评分（回答是否完整）｜④ 质量分（回答准确度）｜⑤ 稳定度（耗时极差倍数）**  
> **关键区分**：**成功率 = 是否完成**，**完成度 = 完成得多完整（是否截断）**，**质量分 = 完成得多准确**。三项必须同时考察，缺一不可。  
> **核心目标**：**又快（效率）+ 又稳（稳定度）+ 又对（成功率+完成度+质量）= 真正可用的模型**

### 1.2 三句话总结

1. **"快且省"才是真效率**：deepseek-v4-pro 在 600k 海底捞针中以 7.9s+2 tokens 做到"用 2 个字解决问题"，是"少即是多"的最佳实践。
2. **高 tokens/s 是陷阱**：Minimax-M3 在数学题中生成速度 93.9 t/s，但因输出 1429 tokens 反而效率垫底；gpt-5.5 纯生成 128 t/s 也因首 Token 21s 而拖累。
3. **稳定性决定可用性**：mimo-v2.5-pro 在 openClaw 任务中耗时 4.4s ~ 178.8s，差出 40 倍；glm5.2 在工具调用任务中成功率仅 50%，都不建议直接用于生产。

### 1.3 关键洞察（8 条）

- 🔍 **洞察 1**：5 个场景中"总耗时最短"和"输出最少"几乎总是出现在同一模型身上，**精炼度直接决定总耗时**。
- 🔍 **洞察 2**：**首 Token 时间（TTFT）是隐形炸弹**——gpt-5.5 在 4 个场景中首 Token 延迟都在 11~21s 之间，是其从未夺冠的核心原因。
- 🔍 **洞察 3**：**任务类型决定模型表现**——deepseek 在"精炼指令"和"长输出"两端都强，Minimax-M3 在"中长输出+工具调用"场景占优，glm5.2 在工具调用类任务上表现欠佳。
- 🔍 **洞察 4**：**"高 tokens/s"反而是低效标志**——Minimax-M3 在数学场景 93.9 t/s 但输出 1429 tokens/轮，是其他模型的 350 倍，纯属浪费。
- 🔍 **洞察 5（新增）**：**成功率 < 100% 是硬伤，不可入生产**——glm5.2 在 openClaw 场景 50% 失败、数学场景 70% 失败（8 轮成功 3 轮无输出），**单项失败率 > 30% 就代表 1/3 用户拿不到答案**。生产候选模型必须五场景均 100% 达标。
- 🔍 **洞察 6（新增）**：**完成度 < 8 = 不可入生产**——mimo-v2.5-pro 在项目构建场景完成度仅 5–7、API 更新 6–7（3 次截断），**意味着用户付了钱却拿不到完整答案**。**完成度独立于成功率**：成功率 100% 不代表交付完整，必须同时考察完成度。
- 🔍 **洞察 7（新增）**：**质量分不能被“看起来快”掩盖**——mimo-v2.5-pro 项目构建场景质量分 5–9、API 更新多次出现内容不完整，**即使总耗时偶尔到 4.2s，质量未达标依然是“耍流氓”**。选型必须“完成度 × 质量分”同时看，不能只看一面。
- 🔍 **洞察 8（新增）**：**完成度与质量分是独立维度**——**完成度 = 交付的多完整**，**质量分 = 回答的多准确**。mimo 项目构建完成度 5–7 + 质量分 5–9 = “又截断又不准”；gpt-5.5 完成度 9.4 + 质量分 9.5+ = “完整且准确”。**选型必须同时考察，不能含混**。
- 🔍 **洞察 9（新增）**：**稳定度 = 生产可预测性**——gpt-5.5 极差 1.8× 反而是“隐形的稳定之王”，mimo 13.9× 平均极差（最高 40.8×）是“定时炸弹”。**生产环境应选择极差 < 5× 的模型**。

#### 场景 1️⃣：600k 海底捞针

- **场景名称**：海底捞针测试 600k（Needle-in-a-Haystack 600k）
- **测试目的**：测试模型在 **60 万字超长上下文**中的**信息定位 + 精炼回答**双重能力，揭示“高 t/s 速型选手 vs 精炼型选手”的本质差别。
- **测试提示词要点**：
  - **输入**：一段 **600,000 字符**（约 60 万中文字）的长文档作为上下文
  - **任务**：在文档中定位某个“埋入”的特定信息（例如特定事件的发生比例）
  - **输出要求**：**“只输出一个百分比”**——极简输出（仅 2-5 token 量级）
  - **设计意图**：量化评估模型“在长上下文中不废话”的能力——是 RAG 系统最讲成本与延迟的关键
- **生产应用场景**：
  - **RAG 系统**（检索增强生成）：从企业知识库/文档集中提取关键信息
  - **法律/医疗长文档分析**：合同、病例、报告中的“关键信息”定位
  - **代码库全局搜索**：在百万行代码中定位特定函数/接口
  - **报告数据提取**：财务/业务报告中“关键指标”快速定位
- **测评重点**：精炼度 vs 输出速度。**deepseek 输 2 token 拿 7.9s 冠军，Minimax-M3 输 159 token 同样 9.5s但“严重注水”**。

#### 场景 2️⃣：数学能力测试

- **场景名称**：简单数学计算（如计算 `-16.95`）
- **测试目的**：测试**基础数学计算能力 + 极简任务的“反冗余”能力**。设计上故意用“超简单”题，验证模型是否能避免“答案 + 解释”这种”习惯性冗余”。
- **测试提示词要点**：
  - **输入**：表达式 `-16.95` 或类似加减乘除表达式
  - **任务**：计算该表达式的值
  - **输出要求**：**直接给出答案**（4 token 量级）
  - **设计意图**：验证模型在“一眼出答案”的任务上是否能“闭嘴”——某些模型会忍不住输出“我们先来计算 ...”这类问候。
- **生产应用场景**：
  - **教育辅导**：AI 老师、学生问答场景
  - **金融计算**：费率、利息、汇率快速计算
  - **报表计算**：表格、时间、比例、增减幅
  - **数据分析**：业务指标快速查询
  - **公式问答**：如 Excel/SQL 辅助
- **测评重点**：**越简单越能看出模型“能不能闭嘴”**。**Minimax-M3 输出了 1429 tokens/轮，是其他模型的 350+ 倍**——在数学题中是一种“变相失败”。

#### 场景 3️⃣：项目构建测试

- **场景名称**：完整项目开发计划 + 代码生成
- **测试目的**：测试**长输出场景（6000-8000 tokens）下的任务完成效率**，证明模型“不是只能输出短回答”。
- **测试提示词要点**：
  - **任务**：生成一个“项目级”的开发计划（含架构设计 + 实际代码 + 说明文字）
  - **输出量级**：**6000-8000 tokens**（项目级，不是“示例”）
  - **包含要素**：架构图、项目结构、核心代码、实现说明
  - **设计意图**：让模型有机会“展开讲”——看它是否在长输出中保持“精炼 + 不冗余”。
- **生产应用场景**：
  - **代码生成**：AI 代码助手（如 Copilot、通义灵码）
  - **项目规划**：PRD 撰写、项目计划、项目设计
  - **技术文档**：API 文档、系统设计文档、架构文档
  - **需求分析**：业务需求转技术方案
  - **示例工程**：Demo 项目、示例代码、教学代码
- **测评重点**：长输出场景下**“多输出”还是“多废话”**？**deepseek 输出 6912 tokens 以 93.14s 夺冠**——长输出也能又快又准。

#### 场景 4️⃣：API 更新测试

- **场景名称**：社交平台后端架构设计（含图表 + 伪代码）
- **测试目的**：测试**中等输出（2000-4000 tokens）+ 多模态元素（Mermaid 图 + 伪代码）**的生成能力，贴近“真实生产中的架构设计任务”。
- **测试提示词要点**：
  - **任务**：设计一个社交平台后端架构
  - **输出量级**：**2000-4000 tokens**（中等）
  - **包含要素**：**架构图（Mermaid）** + **API 伪代码** + 说明文字
  - **设计意图**：输出不仅仅是纯文字，还包含图表、代码块——考查“代码 + 文档”综合输出能力。
- **生产应用场景**：
  - **系统架构设计**：微服务架构、后端架构、数据库设计
  - **API 设计文档**：OpenAPI/Swagger、GraphQL Schema
  - **PRD 产品文档**：产品需求文档、技术方案
  - **架构 Review**：技术评审、架构决策记录（ADR）
  - **原型设计**：快速产出可评审的架构原型
- **测评重点**：**“中等输出 + 多模态”**场景。**Minimax-M3 以 34.17s + 2692 tokens 夺冠**——输出既精炼又生成快。

#### 场景 5️⃣：openClaw 工具测试

- **场景名称**：openClaw 信息收集与文档编写（含工具调用）
- **测试目的**：测试 **Agent 工具调用场景**下的任务完成效率。这是“智能体（AI Agent）”场景的真实写照——LLM 需调用工具、与环境交互、最终输出文档。
- **测试提示词要点**：
  - **任务**：信息收集 + 文档编写
  - **工具调用**：**包含核查与反馈机制**（Agent 场景下的“工具调用”）
  - **输出量级**：**< 1000 tokens**（文档型输出）
  - **设计意图**：真实复现 Agent 场景中的“多轮交互 + 工具调用”模式，考查“工具调用”下的真实效率。
- **生产应用场景**：
  - **智能体（Agent）系统**：AutoGPT、CrewAI、LangGraph、openClaw
  - **RAG + 工具集成**：问答 + 检索 + 计算 的复合系统
  - **自动化工作流**：AI 报告自动生成、新闻摘要、智能报告编写
  - **AI 编程助手**：含工具调用能力的 Cursor/Copilot/通义灵码
  - **多智能体协作**：多 Agent 协作任务
- **测评重点**：**工具调用场景的真实表现**。**Minimax-M3 以 9.705s + 420 tokens 夺冠**——既快又精炼，是 Agent 场景的最佳选择。

#### 💡 五场景互补逻辑

> **这 5 个场景不是“随机选的”，而是“三大类任务”的样本代表**：

| 任务类型 | 代表场景 | 重点考查能力 |
|----------|----------|--------------|
| **极简输出类**（1-10 tokens） | 600k 海底捞针、数学题 | “能不能闭嘴”、精炼度 |
| **中等输出类**（1000-4000 tokens） | API 更新、openClaw | 中等输出 + 工具调用 / 图表 |
| **长输出类**（5000+ tokens） | 项目构建 | 长文生成 + 精炼保持 |
| **多模态类** | API 更新（Mermaid + 伪代码） | 图表 + 代码 综合输出 |
| **Agent 类** | openClaw | 工具调用 + 多轮交互 |

> **为什么选这 5 个**？因为它们覆盖了：**(1) 极简到极长的输出跨度**（2-8000 tokens）、**(2) 纯文到多模态**（纯文本 → 图表 + 伪代码）、**(3) 单轮到 Agent 交互**（一轮生成 → 工具调用）、**(4) 准静态到强动态**（数学题 → 信息收集）。**是"任务效率"选型的最小完备集**。

## 6. 关键洞察 & 反直觉结论

### 🔍 洞察 1：tokens/s 高反而是低效标志

**反直觉点**：平时大家会追求"高 tokens/s"，但本次测评中，**生成速度最快的模型往往是效率最低的**。

| 场景 | tokens/s 冠军 | 实际效率排名 |
|------|---------------|--------------|
| 600k 海底捞针 | Minimax-M3（90.3 t/s） | ❌ 第 3 名 |
| 数学能力 | gpt-5.5（128.4 t/s） | ❌ 第 2 名 |
| 项目构建 | gpt-5.5（77.5 t/s） | ❌ 第 3 名 |
| API 更新 | Minimax-M3（82.1 t/s） | ✅ 第 1 名 |
| openClaw 工具 | Minimax-M3（126.2 t/s） | ✅ 第 1 名 |

**结论**：在 API 更新和 openClaw 工具场景中，Minimax-M3 的高 t/s 配合精炼输出确实夺冠；但在 600k 海底捞针、数学、项目构建 3 个场景中，**纯生成速度 0.3~76 t/s 的 deepseek-v4-pro 反而夺得总耗时冠军**。这说明：**当输出 Token 极少时，生成速度不再是瓶颈，精炼度才是关键**。

### 🔍 洞察 2：首 Token（TTFT）是隐形炸弹

**反直觉点**：gpt-5.5 纯生成速度全场最高（128.4 t/s），却从未夺冠，问题全在首 Token。

| 场景 | gpt-5.5 的 TTFT | 排名影响 |
|------|-----------------|----------|
| 600k 海底捞针 | 9.112s | 略慢 |
| 数学能力 | 16.371s | 中等 |
| 项目构建 | **21.406s** | 致命 |
| API 更新 | **11.989s** | 致命 |
| openClaw 工具 | **18.374s** | 致命 |

**结论**：gpt-5.5 在 4/5 的场景中 TTFT 超过 10s，最长达 21.4s。这意味着用户每次提问都要等 10~21 秒才能看到第一个字——**对一个号称"高速"的模型来说，这是体验灾难**。这也是 gpt-5.5 5 场景 0 夺冠的核心原因。

### 🔍 洞察 3：任务类型决定模型表现，没有"全能王"

**反直觉点**：Minimax-M3 在 2 个场景夺冠，但在 3 个场景"严重注水"——不存在"放之四海皆准"的最优模型。

| 模型 | 夺冠场景 | 垫底场景 |
|------|----------|----------|
| **deepseek-v4-pro** | 600k / 数学 / 项目构建 | 无（最差也是第 2） |
| **Minimax-M3** | API 更新 / openClaw 工具 | 600k（159 tokens） / 数学（1429 tokens） |

**结论**：deepseek 是"双栖王者"（精炼+长输出都强），Minimax-M3 是"专项冠军"（中等输出+工具调用强，但遇到"短答案"任务会"话痨"）。**选型必须按业务场景匹配，不能"一招鲜吃遍天"**。

### 🔍 洞察 4：稳定性 > 速度峰值

**反直觉点**：mimo-v2.5-pro 在某些轮次能跑到 4.2s（比 deepseek 还快），但平均下来反而是全场最慢。

| 模型 | 最快轮次 | 最慢轮次 | 极差倍数 |
|------|----------|----------|----------|
| **mimo-v2.5-pro** | 4.201s | 178.815s | **42.6 倍** ❌ |
| **Minimax-M3** | 6.131s | 14.713s | 2.4 倍 |
| **deepseek-v4-pro** | 4.458s | 106.531s | 23.9 倍 ⚠️ |
| **gpt-5.5** | 6.340s | 19.509s | 3.1 倍 ✅ |
| **glm5.2** | 9.572s | 19.230s | 2.0 倍 ✅ |

**结论**：mimo-v2.5-pro 的 4.2s 极速完全被 178.8s 的灾难性慢速拖垮——**"过山车模型"在生产环境中是定时炸弹**。选型时，**稳定性比速度峰值更重要**。

### 🔍 洞察 5：成功率 < 100% = 不可用

**反直觉点**：glm5.2 在 4/5 场景成功率 100%，但在 openClaw 工具场景成功率仅 50%——这个"局部短板"足以让其退出生产候选。

| 模型 | openClaw 成功率 | 影响 |
|------|-----------------|------|
| **glm5.2** | **50%** | ❌ 不可用 |
| 其他 4 款 | 100% | ✅ 可用 |

**结论**：在选型时，**任何场景下成功率 < 100% 都意味着 50% 概率用户拿不到答案**——这不是"性能问题"，而是"可用性问题"。glm5.2 在 openClaw 场景的 50% 失败率是硬伤。

### 8.1 测评方法论（五维评价体系 · 剔除网络波动后）

> **总轮次**：5 场景 × 10 轮 = 50 轮总测试/模型。**本报告所有数据均取原始 50 轮样本**。
> **重要修正**：**本报告采用"剔除网络波动后"的五维评价**——glm5.2 原始 8 轮“超时无答案”判定为网络/API 偶发失败（成功轮次 100% 正确），成功率视为 100%。**mimo / gpt-5.5 / Minimax-M3 / deepseek 的所有问题均为模型本身**（如 mimo 项目构建 5–7 完成度），不需剔除。

#### 8.1.1 五个评价维度

| 维度 | 定义 | 量化指标 | 合格门槛 |
|------|------|----------|----------|
| **① 效率** | 任务完成的速度与精炼度 | 总耗时（秒）+ 输出 Token 数 | 总耗时越短 + Token 越少越好 |
| **② 成功率** | 任务能完整完成的概率 | 10 轮中成功轮次比例（%） | **生产候选必须 100%** |
| **③ 完成度** | 任务交付的完整程度 | 原始 9–10 分制评分（**是否截断**） | **平均 ≥ 8.0** |
| **④ 质量分** | 任务完成的准确度 | 原始 9–10 分制评分（**答案准确性**） | **平均 ≥ 9.0** |
| **⑤ 稳定度** | 任务耗时的可预测性 | 耗时极差倍数（最快/最慢） | **生产候选需 < 5×** |

> ⚠️ **关键区分**：**完成度（③）= 交付得多完整**；**质量分（④）= 回答得多准确**。两者是独立维度，必须同时考察。

#### 8.1.2 原始数据指标

- **总耗时（s）**：从请求发送到完整响应的总时间
- **输出 Token 数**：模型返回的 Token 总数
- **成功率（%）**：10 轮中输出有效 Token 且答案正确的轮次比例
- **完成度评分**：从原始报告"评估结果"中提取，衡量回答是否完整（是否截断）
- **质量分评分**：从原始报告"评估结果"中提取，衡量回答准确度
- **TTFT（首 Token 时间）**：从发送到模型返回第一个 Token 的时间
- **TPFT（生成阶段时间）**：总耗时 - TTFT
- **纯生成速度（t/s）**：输出 Token / TPFT

#### 8.1.3 五维评分公式

> **综合得分 = 夺冠数 × 10 + 成功率(%) × 1 + 完成度 × 5 + 质量分 × 5 + (10 - 极差倍数/10)**，满分 100。
> - 夺冠数权重最高（3 冠 = 30 分）
> - 成功率作为底线门槛
> - 完成度和质量分各占 5%（反映“交付完整度”和“回答准确度”）
> - 极差越小稳定度越高

#### 8.1.4 选型门槛（生产环境）

| 维度 | 最低要求 | 说明 |
|------|----------|------|
| 成功率 | **100%** 五场景 | 任何场景 < 100% = 不可入生产（如 glm5.2） |
| **完成度** | **≥ 8.0** 五场景 | < 8 代表存在明显截断（如 mimo 项目构建 5–7） |
| **质量分** | **≥ 9.0** 平均 | ≤ 8 代表存在明显质量问题（如 mimo 8.5） |
| 稳定度 | **极差 < 10×** | > 20× 代表严重不可预测（如 mimo 600k 场景 20.9×） |
| 效率 | 视业务场景而定 | 可按业务类型选不同模型 |
